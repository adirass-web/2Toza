# Toza copy and funnel revision plan

Review draft · 17 November 2026 · Baseline main e9a13c8fecf5171dd2d15cc5e6673be93753e7e2

Goal: make the existing personal, in-person protection service easier to understand and contact. Preserve its restrained voice, factual scope, prices and client control. The critique combines the initial review with independent premium-service and conversion/UX reviews. No conversion analytics or customer interviews were supplied; the recommendations are hypotheses to validate.

## Decisions carried into this draft

1. Keep the emotional home headline, existing situation paths, published tier prices and protection-first pricing emphasis.
2. Add visible WhatsApp and Signal actions where the copy invites contact. Explain that a tap opens messaging; it does not book an appointment or start a call.
3. Explain the service and named expert earlier on Home. Bring existing consent and credential-control information near the pricing comparison.
4. Show the sequence early on Pricing: free conversation, separately purchased assessment, separately agreed protection. Keep the exact assessment-credit condition alongside it.
5. Replace broad risk-mitigation/confidentiality claims with scoped, supportable statements; preserve the professional-history facts without implying institutional endorsement.
6. Retain the long situation imagery for this wording review. A shorter mobile version is a later layout prototype, not an approved change.
7. Do not add testimonials, outcome percentages, urgency, guarantees or premium-status language without evidence.

## Review the copy deck

The HTML deck includes every English page's current main content, a proposed reading version, the exact proposed changes and reasons, shared navigation/contact text, metadata and image/accessible labels. Existing disclosures are expanded for reading. Editorial proposal blocks are labelled; they are not product sections to publish verbatim. Matching a change to a rendered paragraph is checked by the generator. Current text is preserved separately so no omission is silently approved.

Confirm wording and hierarchy first. Confirm any missing service area, languages, scheduling and first-contact handling facts before adding them. These facts are not invented in the deck. Proposed copy is not approved by inclusion here.

## Update the live site after copy review

1. Freeze an approved revision list and identify accepted layout moves. Record any rejected variants and facts still awaiting confirmation.
2. Branch from current main. Map changes to the actual sources: approvedEN.js for Home; locked approved Markdown for Exposure, How it works and About; the situation/legacy content files; Pricing template; shared contact/navigation includes. Update approved-copy baselines and parity checks intentionally, without broadening them to accept unrelated changes.
3. Implement visible channel actions and the buying-sequence orientation first. Keep contact URLs accurate and prices/allowances sourced from facts.json. Use anchors or headings for discoverability without duplicate IDs. Preserve the preview profile's noindex.
4. Integrate accepted copy and hierarchy moves. Check phone and desktop compositions, text contrast, touch targets, keyboard focus, native disclosures, reduced motion, printing and all contact destinations. Do not send test messages.
5. Run both build profiles, copy/fact parity, links/anchors, accessibility, performance and existing browser gates. Review the diff independently. Publish a new Cloudflare preview from the verified branch.
6. Review that preview against this deck and repeat a live SquirrelScan/browser check. Separate deliberate preview SEO warnings from faults. Measure click placement/channel only with an agreed privacy-conscious setup; clicks do not equal conversations or sales.
7. Merge the approved, verified PR into main. Verify the resulting main build and publish the exact verified build to the chosen existing Cloudflare site. Use its pages.dev address until a domain is selected. Record deployment ID, commit and previous working deployment for rollback; smoke-test the public URLs after publication.
8. When a domain is chosen, separately configure Cloudflare DNS/custom-domain binding and validate canonical URLs, sitemap, indexing, public TLS, social metadata and any CSP/HSTS policy. HSTS subdomain scope requires an explicit infrastructure decision. Domain purchase is a separate action.

## Acceptance criteria

A visitor can identify the service, the expert and the first step from the home introduction; open a correctly labelled messaging channel; explain the assessment fee, separate protection decision and exact credit rule; and find device/account scope and terms without relying on marketing claims. Test these tasks with intended clients or advisers. No performance or conversion improvement is claimed before measurement.
